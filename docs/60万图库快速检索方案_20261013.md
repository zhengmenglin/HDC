# 60 万级图库快速检索方案（待确认）

日期：2026-10-13
背景：目标图约 400 张、图库约 60 万张；现有"逐图 Python 比对"路线在 60 万规模下不可行。
状态：**方案草案，等老大确认后再动代码**（本轮只做实测与方案，未改任何工具代码）。
实测环境：RTX 3060 12GB（torch 2.2.0+cu118 就绪）/ CPU 12 核 / D 盘剩余 42GB。

## 0. 一句话结论

三个杠杆，按收益排序，组合使用：

1. **元数据分桶**（你的思路）：带日期/机号的查询只扫对应录制组 → 秒级~分钟级
2. **索引化 + 并行**：把"挨个比"变成"一次建库、多次秒查"
3. **GPU**：只用在两个确切落点（建库提取、全库扫描引擎）

任何一步单独做都吃亏：不分桶 → 白扫 60 万；不建库 → 每次从头再来；只上 GPU → 解码仍卡在 CPU。

## 3. 方案：三级漏斗

### L0 元数据分桶（第一优先，改动小见效快）

```
规则解析（查询 + 语料库全量文件名）→ 录制键
  T1 同录制键（日期+机号+录制号完全一致）
  T2 同日期+机号
  T3 同日期
  T4 无信息（含"上面各级均未找到达标结果"时的降级目标）
执行：T1 扫完、达标即停；不达标自动降级进入下一层（安全阀，默认开，可关）——保召回
报告：命中行标注层级（T1 命中≈强证据；其余按现有双证据口径）
```

- **按需建索引**：只先给"查询涉及的录制组"建索引（例：50 组 × 2000 张 = 10 万张，
  12 进程约 50 分钟）；其余语料暂不处理或后台补——先把最痛的部分解决。
- 对"无信息"查询：直接走 L1 全库引擎（即你说的"再对比剩下的没有日期信息的"）。
- 语料侧剩余：T1/T2/T3 未覆盖的语料，按同一机制在 T4 层兜底扫描。

### L1 扫描引擎（全库粗筛，两实现，二选一或互为兜底）

- **CPU（现成算法，先行）**：位移投票并行化，36s/查询 → 分片多进程 ≈3s/查询
- **GPU（新引擎）**：类别剖面 1D 互相关 → 每图峰值取 top-K 候选（≈3~12s/查询，60 万全体）
- **建库加速（GPU 第一落点）**：GPU 颜色分类 + CPU 连通域混合 ≈150ms/图 → 12 进程 2.1h
  （更激进：剖面法全 GPU 提取，需先做"与现标记表等价性"验证）

### L2 复核（口径不变：宁缺勿假）

- 覆盖率 + NCC 双证据保持；复核对象 = 各层筛出的 top-K 候选
- 分层预算：T1/T2 命中全量复核；T4 收紧 top-K（候选解码是隐藏成本，每张 ~60ms）

## 4. GPU 用在哪（诚实清单）

| 用途 | 实测收益 | 结论 |
|---|---|---|
| 建库颜色分类 | CPU ~300ms → GPU 9.9ms/图 | ✅ 先上 |
| 全库扫描（剖面相关） | 60 万 ≈3s/查询 | ✅ 召回验证通过后上 |
| NCC 复核 | 卡在 PNG 解码（CPU/IO） | ⚠️ 帮助有限，靠候选预算控制 |
| 整图原始像素 NCC 进 GPU | 判别信息仅占 0.1% 像素，伪峰治不了 | ❌ 不做（10-10 已实测） |

明确不用的算法：感知哈希 pHash（只能整图去重，不能"片段定位"）；
深度学习嵌入（标注成本 + 不可溯源，与既定结论一致）；相位相关（本质=剖面相关，已含在 GPU 引擎）。

## 8. 增补：格式实况 + 新算法验证（2026-10-13 晚）

### 8.1 图库/查询格式实况（据截图确认）

- **图库 = 每"录制"一个文件夹**，文件夹名四种形态：
  `YYMMDD_HHMM_机号`（如 `240105_0730_21869`）、`YYMMDD_机号`（`180424_16018`）、
  纯机号（`18277`、`18369`）、中文描述（`2021.1.14欢河数据`）
- 文件夹内 = `<文件夹名>_Step-N.png`（N=0,1000,2000,…，与 0646 同族）；
  **1888×512、约 19KB/张** ⇒ 60 万张全库 ≈ 12GB（磁盘/IO 压力远小于预估）
- 查询图：512×512、约 8KB/张；命名混杂但 token 可挖：前缀标签（`1孔孔裂`、`19_`）、
  全日期 `YYYYMMDD`、`YYMMDD_HHMM_机号` 片段、纯机号前缀（`18277_…`、`18369_…`）
- **T1 规则升级**：查询名"包含某个图库文件夹名"（token/前缀级）→ 直接锁定该录制组；
  例：`18277_…` ↔ 文件夹 `18277`；`251005_0741_21261…` ↔ `251005_0741_21261*` 文件夹

### 8.2 新算法验证结果（三轮探针，全部实测）

| 实验 | 结果 | 结论 |
|---|---|---|
| 命中区像素一致性 | **99.1% 像素逐字节相同** | 查询≈图库同源渲染；复核可极轻。整列哈希仍不可行（0/512 列全等，差异虽少但散布） |
| 单图·分类剖面 + 原始互相关 | 真位置排名 4（浓密区能量偏置） | ❌ 必须做 NCC 归一化 |
| 单图·分类剖面 + NCC | **真位置排名 1，NCC=0.985** | ✅ 剖面 NCC 是有效匹配算法 |
| 相似簇干扰 | 另一处相似簇达 0.945 | 单峰值不可靠 ⇒ 一律 top-K + 复核（宁缺勿假） |
| 拼接单次相关（初版） | 真位置第 6、峰值偏 1415px | ⚠ 根因已定位：**非零覆盖归一化缺陷**（真实内容与空区被平均 ⇒ 削半降分）；修法明确，列为阶段 C 实验项 |
| GPU 相关吞吐 | 64k 列拼接 10ms/次 | 全库（÷4 降采样）外推 ≈ 1~3s/查询 |

### 8.3 GPU 算法菜单（更新版）

1. **建库：GPU 颜色分类**（30×，实测 9.9ms/图）→ 全库建库 4.9h → 约 2h（12 进程）
2. **扫描引擎：分类剖面 NCC（GPU 批量）** ← 本轮验证的核心
   - 每图只存 5 类逐列计数剖面（≈3KB/图；全库 ~1.8GB，压缩约 0.9GB）
   - GPU 批量 NCC（conv1d/FFT）→ 全库 top-K；实测吞吐外推 ≈3s/查询（RTX 3060）
   - 相比现有"标记投票"：更简单、直接给打分排序；**定位为候选生成器**，top-K 必过复核
3. **拼接单次相关**（研究项）：修复归一化后复测；若成立，全库一次相关给出唯一位置
4. 复核阶段：像素 99.1% 一致 ⇒ 双证据可简化；GPU 帮助有限（PNG 解码在 CPU）
5. 不推荐：整图原始 NCC 进 GPU、pHash、深度嵌入（理由见 §4）

### 8.4 实施路线（在 §6 基础上的更新）

- **A**（不变）：文件名解析器 + 分层调度 + 目录普查工具（1~2 天，立即可测）
- **B**：全库"剖面库/标记库"构建（GPU 分类 + 12 进程 ≈2h，分片缓存、断点续跑）
- **C**：GPU 剖面 NCC 扫描引擎 + 召回验证（0646 已知答案为基准，要求 100% 召回）
- **C2**（可选）：拼接单次相关（先修归一化，再验证）
- **D**：GUI 集成 + 回归测试
