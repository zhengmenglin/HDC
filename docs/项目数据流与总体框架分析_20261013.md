# 项目数据流与总体框架分析

日期：2026-10-13（分析稿 · 待确认）
关联：`docs/60万图库快速检索方案_20261013.md`、`docs/项目评审与工作计划_20261010.md`、`docs/软件详细设计.md`

## 0. 一句话结论

本项目是一条完整的研究流水线：**数据准备 → HDC 点级识别 → 与视觉识别对照 → 论文**。
当前最紧的瓶颈不是算法，而是「带标签数据」——60 万图库检索工具就是解决它的"数据发动机"。
优先级排序：**数据准备 >> 算法修复 > 对照实验 > 论文写作**。

## 1. 三个目标与串联逻辑

| 目标 | 内容 | 现状 |
|---|---|---|
| G1 工程 | PC 端 HDC 伤损识别（点级分类，9 通道滑窗） | 骨架完成；P/R/F1=0，根因链已定位（数据 + 工程缺陷） |
| G2 数据 | 60 万 B 显图库 → 大规模带标签样本 | 方案已出（10-13），工具族已实战（22/22 回归） |
| G3 研究 | 论文：超维计算 vs 视觉识别 对比 | 今日明确；本分析给出框架 |

**为什么 G2 先行**：G1 的第一瓶颈是数据——训练集仅 1 个文件、通道 6/7 零正样本、
原型 178/180 为零 ⇒「0 预测」的第一层原因就在数据。G2 把标注成本从"每点手工"降到
"检索 + 弱标签 + 抽检"，这是 G1/G3 成立的前提。

## 2. 全景数据流（四层）

### L0 数据源

- 探伤仪录制 → 原始数据 JSON（编码值 / 深度 / 通道 …）
- B 显渲染图（1888×512、~19KB、带彩色标记）→ **60 万图库（每录制一文件夹，`_Step-N.png`）**
- 两者是同一录制的"数字孪生"（图 ↔ 数据一一对应：285.67 px/m、0 点=画布中心 x=945）

### L1 数据准备（当前主战场）

```
60万图库 ──[元数据分桶 T1~T4]──> 目标录制组（几百~几千张）
        ──[GPU 扫描引擎（分类剖面 NCC / 拼接相关）]──> 候选段
        ──[双证据复核（覆盖率 + NCC）]──> 命中清单（录制 / step / x 区间）
命中段 ──[图内标记 → 类别]──> 弱标签候选（紫=核伤、砖红=螺孔/伤损点、绿/青/蓝=待普查）
       ──[x_px → 里程 → encoding 区间]──> 映射到 CSV 行（点级样本）
       ──[GUI 抽检修订]──> 修正标签 + 噪声率报告

产出 ① 点级样本池（HDC 用：encoding + 9 通道序列 + 标签）
产出 ② 片段图池（视觉基线用：B 显片段 + 标签）
—— 一套数据、两种用法 = 论文公平对比的地基
```

- 双用途：**定向检索**（找指定图案，工具已具备）+ **全库弱标签收割**（为论文数据集，建库时顺带产出）
- 需新增：结构化「标注迁移表」导出器（录制/step/x范围/类别/置信度 → encoding 区间）

### L2 转换与标注（已有链路，格式已核实）

- JSON →（`ultrasonic_data_converter.py`：拼孔 / BeamOffset）→ `*_hdc.csv`（encoding + channel_0-8）
- GUI 人工标注 → `*标注.json`（真实格式已核实）：
  `{type, subtype{id,name}, points[{e, channel, depth, amplitude}], start_E, end_E, channels}`
- 标签体系（`gui/type_selector.py`）：伤损类（核伤 1–6 细类、螺孔裂纹 11 …）；
  结构类（接头 / 螺孔 / 鱼鳞伤 / 轨底锈蚀 / 道岔 …）

### L3 训练

- **HDC 侧**：滑窗（WINDOW=128 / CENTER_IDX=63）→ 超维编码（Level ⊕ bind(通道) ⊕ bind(位置)）
  → 9 通道独立原型（Centroid / OnlineHD）→ 点级分类
  ⚠ 待修清单：`_create_encoder` 缺失、编码与原型必须同源、Level 单 span 分辨力、指标混算
- **视觉侧**：见 §5（两个赛道）
- **切分纪律**：按「录制」分组划分 train / val / test，禁止随机抽点
  （步进图相邻重叠 888px ⇒ 同录制跨集会泄漏）

### L4 评估与论文

- 统一指标：P/R/F1（点级口径冻结）+ 数据效率曲线 + 延迟 + 模型体积 + 边缘可行性 + 可解释性
- 论文图表：B 显渲染示意、混淆矩阵、效率曲线、延迟/体积对比、原型与热力图可视化
- **方法学卖点**：「视觉检索为 HDC 做数据准备」的混合流水线本身可写进论文方法章节

## 4. 关键设计决策（论文成败所系）

1. **评价单元 = 点级**（窗口中心）；label 0–19 口径、channels 配置、BeamOffset **全部冻结**并写入论文附录
   （历史教训：换 channels 会静默改变分母，指标不可比）
2. **按录制划分数据集**（防 888px 重叠泄漏）；跨录制的同轨段才算独立样本
3. **弱标签三级证据**：检索命中（结构）+ 标记类别 + 抽检修正；论文须报告弱标签噪声率与抽检比例
4. **HDC 侧先修再比**：同源、`_create_encoder`、randomness 复测、指标口径——否则对比无意义
5. **视觉基线共享数据与切分**（同测试点集、同指标函数）
6. **双尺度报告**：点级（HDC 强项）与片段级（视觉强项）分别报，避免"苹果比橙子"

## 5. HDC vs 视觉识别：对比实验协议（草案）

**赛道 A（同数据 · 不同表征）**：输入同为 9 通道声程序列（同窗口协议）；
HDC 超维编码 vs 1D-CNN / Transformer。回答"表征方式带来多大效率差"（小样本、延迟、体积）。

**赛道 B（同任务 · 不同模态）**：HDC（信号输入）vs 视觉（B 显图 2D-CNN，点周围片段）。
回答"视觉模态的红利与代价"（信息量 vs 标注成本 / 算力 / 渲染依赖）。

**统一协议**：同测试点集 + 同划分 + 同指标函数；另报各自的数据效率曲线（n = 10/50/100/500/2000）。

| 维度 | HDC | 视觉（CNN） |
|---|---|---|
| 精度 P/R/F1 | 待测 | 待测 |
| 数据效率（n 曲线） | 预期优势 | 需大量数据 |
| 推理延迟/点 | 预期毫秒级、CPU 可行 | 待测（GPU 有优势但需算力） |
| 模型体积 | 预期 KB~MB | 数十 MB |
| 边缘可行性 | MCU / FPGA 可期 | 需 NPU / GPU |
| 可解释性 | 原型相似度（直接） | 热力图（间接） |
| 标注成本 | 弱标签可用 | 需大量人工框/类 |

**预期结论方向**：HDC 在小样本 / 低功耗 / 可解释上占优；视觉精度上限高但依赖标注与算力；
二者互补——"视觉检索 + HDC 识别"的混合流水线是本案的方法学特色。

## 6. 数据准备闭环与 60 万方案的嵌合

- 60 万方案 A/B/C 的产出直接服务本流水线：
  - **A**（解析/普查/分桶）→ 决定"哪批数据可自动归组"
  - **B**（建库）→ 顺带产出全库标记表 → **全库弱标签收割的原料**
  - **C**（GPU 扫描引擎）→ 定向检索 + 已知缺陷的高召回提取
- 新增需求（写进 A 阶段）：**「标注迁移表」导出器**——把命中/标记统一转成
  `(录制, step, x0, x1, 类别, 置信度, 来源)` 的结构化表，供转换脚本消费生成 label CSV
- 规模估算（待"标记语义普查"后修正）：全库每图若干标记 ⇒ 候选点数万 ~ 数十万级

## 8. 风险清单

- 弱标签噪声 / 漏标 → 抽检比例、噪声率报告、保守类别策略
- 60 万库命名 / 格式不齐 → 普查先行（教训已两次：调色板、命名）
- HDC 修复后仍不达标 → 降级方案：任务改为"片段级 / 区间级检测"（与视觉对齐更自然）
- 论文公平性被质疑 → 协议先冻结、划分与代码公开（附录）
- 时间：全库建库为一次性小时级（可过夜）；写作预留 1~2 周
